# Decisions: issues #11 and #17 (orchestrator starts worker sessions)

Codes continue from the session's #32 grill (specs/007-herdr-workspace/decisions.md, D1 to D11). D11 there belongs to this feature: workers are cross-machine.

- D12 (Q5): O10. Two worker paths: headless `claude -p` for quick local tasks (#11), and a `claude` in its own herdr pane, local or `--machine`, for visible or remote tasks (#17). Rejected: O9, pane only.
- D13 (Q6): O11. A pane worker writes its result to a known file in its worktree and replies with the path; the orchestrator waits with `herdr agent prompt --wait`, then reads the file (over ssh for a remote machine). The headless path reads the `result` field of `claude -p --output-format json`. Rejected: O12, read the result from the pane text with `agent read`.
- D14 (Q7): O13. One question path through herdr: the pane worker asks in its pane, the orchestrator sees the agent `blocked` (`herdr agent wait --until blocked`), reads the question (`agent read`), asks the user, and sends the answer into the pane (`agent prompt` or `send-keys`). The user can answer in the pane directly. Headless workers never ask: no question tool and a turn limit; a question ends the run with the reply as the result. Rejected: O14, SendMessage on the same machine and herdr `blocked` only for remote.
- D15 (Q8): O15. One git worktree per pane worker, made by `herdr worktree create` (worktree, workspace and label in one call, local or `--machine`), branch named by the task; the orchestrator merges on green. The headless path runs in the orchestrator's own folder, one task at a time. User add: when one project is split into phases across workers, the workers must be able to talk to each other and see each other's work, like a development team (shape decided in Q9). Rejected: O16, all workers share the branch folder with files split by task.
- D16 (Q9): O20, the hybrid. Every pane worker gets the roster (names, machines, branches, tasks) and the team rules in its brief: commit each finished unit, fetch before building on a teammate's work, never merge. Same-machine teammates talk with SendMessage by name (cross-session messaging, proved in the #9 spike); cross-machine teammates talk with `herdr --machine <m> agent prompt <name>`. Work is shared through git. Questions to the user go through the herdr `blocked` path (D14) on both machines. The orchestrator runs `st-review` on each branch and is the only merger, so one quality and security gate holds for all. Agent Teams (experimental, same machine, lead-spawned, no herdr panes, no worktrees) is not used; its facts are in the session notes. Rejected: O17 alone (herdr for every message), O18 (hub only), O19 (Agent Teams for local, herdr for remote).
- D17 (Q11): O21. A new skill the orchestrator uses on request ("run T004 in a worker on the laptop", "build US2 with a team of three"): it starts the workers, hands out briefs and the roster, relays questions, collects results, reviews and merges. The existing build loop (`st-build` with Agent-tool subagents) stays as it is. Rejected: O22, every build task runs in a pane worker.
- D18 (Q10): O23. After the result is read and the branch merged, the orchestrator closes the worker's pane and workspace (it made them), keeps the worktree folder and the branch, and names the folder as ready to remove; the user says when. A failed or stopped worker keeps its pane open for reading. Rejected: O24, remove the worktree folder after the merge.
- D19 (orchestrator, not asked): a pane worker is a normal interactive `claude` with the user's plugins; the plan researches how its commit prompt (Stratum's git guard, default `ask`) is answered through the question path or by the worker's own `st-git`. A headless worker gets an allow list of tools, no question tool, a turn limit and a timeout, and never commits.
- D21 (Q12): O27. A pane worker runs on its own with Claude Code's `/goal` (https://code.claude.com/docs/en/goal.md). The orchestrator writes the brief (task, roster, team rules, paths, the Stratum lane to run, the Codex advisor from #18 when merged) to `brief.md` in the worker's worktree, and sends one prompt: `/goal <short condition>; read brief.md in this folder first and follow it`. The condition is short and checkable: the task's test command exits 0, the commit exists, the result file is written. The worker runs in auto mode so `/goal` can run unattended; a question still shows as `blocked` (D14). Headless workers get the same `/goal` form through `claude -p "/goal ..."`. Rejected: O25 (brief as first prompt, `/goal` as a second), O26 (no `/goal`, the orchestrator re-prompts on every stop), the whole brief as the `/goal` text (4,000-character cap, the evaluator cannot judge a roster).
- D23 (user, spec gate, 2026-10-23): the spec is agreed as written (US1 to US5, FR-001 to FR-016, SC-001 to SC-007).
- D24 (Q14): O30. `start` writes `{"commit":"auto"}` into `.stratum/git-guard.json` of the worker's worktree only (git-ignored). Plain commits pass; amend, push, reset --hard and branch delete still ask. Review and merge by the orchestrator stay the gate. Rejected: O31, keep the guard so every worker commit is a question to the user.
- D25 (Q15): O32. Tasks that build on each other run on one machine, so a fetch in that machine's shared repo sees every teammate's branch. Teammates on different machines only exchange messages; no commits cross machines. Rejected: O33, the orchestrator relays commits over ssh with a `bring` subcommand (cannot be proved while the laptop is down).
- D26 (user, plan gate, 2026-10-23): the orchestrator may decide a worker's questions itself. When a pane worker is `blocked`, the orchestrator reads the question and answers it with the `/stratum:st` rule: a small decision (inside the brief, the plan and the task's files: naming, placement, a tool permission for the task's own command, a choice the plan already settles) it answers at once with `answer`; a big one (changes the spec, scope or approach, touches privacy, access, data model, contracts, dependencies, cannot be undone, reaches an audience, costs a lot) goes to the user first. Every answer the orchestrator gave on its own is listed at the end of the run. Headless workers still never ask. Changes US2, FR-006 and the skill's `blocked` step. Rejected: every worker question goes to the user (the D14 wording).
- D27 (user, build phase, 2026-10-23): worker model option. `/stratum:st-worker <task> ... model <name>` sets the model for that worker: a pane worker gets `--model <name>` in the claude args of `herdr agent start`, a headless worker gets `--model <name>` on `claude -p`. Without the option the script reads the `st-worker` entry of `.stratum/models.json` (the file st-model manages, keys `model` and `effort` as for the other agents) and passes its `model` when present; otherwise it passes nothing and the user default applies. The value must be one token matching `[A-Za-z0-9._-]+` before it reaches a command line. The brief says `Model: <name or default>` so the result file names the model that ran. Only `model` is passed; `effort` has no claude flag here and is read but not used. Added as a review-sized change after the planned tasks: spec FR, contract, red test, code, commit.
- D28 (orchestrator, small, 2026-10-23): `hooks/st-models.py` accepts `st-worker` as one extra name beside the agents from `agents/*.md`, so the `st-worker` entry of `.stratum/models.json` (D27) does not block agent starts; a case in `tests/test_model_hook.py` covers it, and `skills/st-model/SKILL.md` lists `st-worker`. File values stay limited to the hook's model list; `--model <name>` from the request takes any one token. Rejected: drop the models.json fallback (narrows D27).
- D24 (amended, PR #41 round 2 F3, 2026-10-23): the worker's `commit: auto` applies only to a plain `git commit` run from the worker worktree. A commit that names another checkout (`git -C <dir> commit`, or a `cd <dir>` segment before `git commit`) asks, because the hook read the guard file from the session cwd upward and such a commit would land outside `<base>..worker-<id>` with no review. Change 001 (guard gaps, 2026-10-23) widens this: `git --git-dir`, `git --work-tree` (both forms), a `GIT_DIR=` or `GIT_WORK_TREE=` prefix and a `pushd <dir>` segment also make the commit ask. `git merge`, `pull`, `cherry-pick`, `revert` and `am` aimed at another checkout ask, in the worker folder they stay unruled. `close` removes the guard file (D30). Known gap left open (gate Q1): `env GIT_DIR=X git ...` and `export GIT_DIR=X` are not seen, so no rule fires for them.
- D29 (orchestrator, PR #41 round 2 F10, 2026-10-23): the default lane in the worker brief is `plain edit, no lane`. The skill passes a Stratum lane (for example `/stratum:st-build, task <id> only`) only when the user names one in the request. Why: no live run has used st-build inside a worker, and st-build ticks tasks.md while the brief forbids editing it. Rejected: keep the st-build default and list the steps the worker must skip (longer brief, still unproven live). Revisit after one live st-build worker run.
- D30 (change 001, guard gaps, 2026-10-23): `st-worker.sh close` deletes `.stratum/git-guard.json` from the worker folder (local `rm -f`, remote `rm -f` over ssh), after the working/blocked and open-PR refusals and before `workspace close`. If the rm fails, close is refused. Rejected: "auto only while worker-<id> is checked out", because the branch stays checked out after close and the hook would need herdr to know the worker is gone. Removed, not neutralized: the file is the repo file merged with `commit: auto`, no original is kept, and the folder is "ready to remove".
