# Decisions: 011 custom design mode (#57)

From the #57 grill, 2026-11-01. The Q, O and D codes start at Q6, O4 and D9, after the codes in #57 and the session handoff. Q9 was dropped: it was about a different FigCraft (a Figma plugin).

- D9 (Q6): O4. Custom design is a third mode, "custom", in `skills/st-design/SKILL.md`. It is the new-look flow with three steps added after the grill: build the design in a design tool through MCP, stop while the user checks and changes it there, read the finished design back. Then the same build, check, gate and commit. Plan offers it as `[screen: custom]`. Rejected: O5, a separate lane.
- D10 (Q7): FigCraft (https://github.com/storytold/figcraft: a native Rust design app for Linux, macOS, Windows and the web, free, MIT or Apache-2.0, alpha; its MCP server `figcraft-cli mcp --attach <port>` drives the open app live) is the default design tool. Other design tools with an MCP server stay an option. Rejected: the official remote Figma MCP as default (paid plan for canvas write), Claude Design, Penpot.
- D11 (Q8): O6. A gate in the chat: the lane stops after it builds the design in the tool and tells the user to change it there. Any reply that says the design is good ("done", "looks good", and so on) starts the read-back. Rejected: O7, the lane checks the tool by itself.
- D12 (Q10): O10. On "good", the lane saves the design as a `.figcraft` file in the project, committed with the screen, and writes the design file (`DESIGN.md` + `.impeccable/design.json`) from its variables and styles. The build agent reads the saved file with the CLI, no window (`figcraft-cli info`, `render`, `export`: layout + PNG) and the design file, so the build needs no open app and fix rounds read the same design. Rejected: O11, the build reads only the design file (the screen's layout is lost).
- D13 (Q11): O12, with the user in charge. At the gate, the user says how each change is made: in the tool (change the design, say it is good, the lane saves, reads and builds again) or in code. When the user does not say, layout and look changes go to the tool and small code-only fixes stay in code. Rejected: O13, all changes in code only.
- D14 (Q12): O14. Build only the FigCraft path now. The tool's steps live in one file beside the skill, `skills/st-design/design-tool.md`, as `engine.md` names the engine. A later tool is a new copy of that file and one setting. Rejected: O15, FigCraft plus a second tool now.
- D15 (Q13): O17. The lane starts FigCraft itself (`figcraft --control 7979`) when the port does not answer, as it starts a Codex review or a herdr workspace: part of autonomous work. A dev server is different: it hides in a terminal, while FigCraft is a window the user can see and close. Rejected: O16, the user starts it.
- D16 (Q14): The start of the first design depends on the task. Most common: improve the design while the user keeps the existing look (colors, fonts). Then there is no theme pick: the first design in FigCraft takes its variables from the existing design file, or from the code's tokens when there is none. For a new look or an overhaul: O18, the theme pick, and the picked theme's tokens go into FigCraft as variables. Either way, after "good" the tokens and the design file come from FigCraft's variables. The lane picks the start with section 1 step 4's new-look rule. Rejected: O19, never a theme pick.
- D17 (Q15): O20. The custom mode also takes an existing screen: the agent first draws the current screen in FigCraft from its code and a screenshot, the user changes it, and the lane builds the code again. Entry: `/stratum:st-design`, or `/stratum:st` sends a task that asks for custom design to the Design lane. Plan is unchanged and marks only new screens. Rejected: O21, new screens only.
- D18 (Q16): O24. MCP, attached to the app the lane starts (`figcraft --control 7979`, D15), for live work. The MCP server config goes in `.claude-plugin/plugin.json`, so it is in one place and on both machines. The `st-design` agent gets the FigCraft MCP tools. It draws live, sees the user's selection and unsaved changes, and saves the file when the user says it is good. The build still reads the saved file with the CLI (D12). Plan must test that a plugin subagent can call the plugin's MCP tools. Rejected: O22, CLI only (no live view, no selection, save by hand).
- D19 (Q17): O25, plus an offer at install. `st-design-check.sh --custom` also checks `figcraft` and `figcraft-cli`, only for the custom mode; a missing one stops the run before any work with the install link. `st-status` shows FigCraft as optional, "for the custom mode". `st-init` offers FigCraft as an optional install: on yes, it gives the exact install command for the machine. Rejected: O26, check it on every Design lane run.
- D20 (Q18): O27. The lane starts FigCraft with `--automation-read-root <project>` and `--automation-write-root <project>/design`. The agent cannot reach files outside the project, and FigCraft's sharing is off, so no design goes to a public server. Rejected: O28, no limits.
- D21 (Q19): O29. One stop before the code build: the FigCraft stop. The lane writes the design file after "good" and shows it at the gate with the screenshots, where the user can still change it. Rejected: O30, a second stop to confirm the design file.
- D22 (Q20): O31. On the user's FigCraft yes, `st-init` adds one allow rule for the FigCraft MCP tools to the project's `.claude/settings.json` (committed, so both machines get it). No permission prompts in a run. Rejected: O32, no rule (up to 11 prompts per project and machine).
- D23 (Q21, Inspect F11): O33. The D22 allow rule lists the same 11 FigCraft tool names the `st-design` agent uses, not the whole server. UI input tools (`pointer`, `key`, `type_text`) still ask first. Rejected: O34, the server-wide rule with a corrected security note.
