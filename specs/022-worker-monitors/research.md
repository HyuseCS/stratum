## Decisions

### R1. Where an approval request comes from in a worker

- Decision: in an auto-mode worker, a request comes only from a prompt that auto mode still shows: an explicit `ask` rule, or a hook `ask`. A worker's commit is `commit: auto` (`scripts/st-worker.sh:337`), so a commit never asks. The git guard asks for `git rebase`, `git branch --force` and a few more (`hooks/st-git-guard.py:309-319`). The approve hook writes a request only when the command passes `bash_ok` or the edit passes `edit_ok` (`hooks/st-approve.py:307-316`). An `ask` rule matches the exact command text, so the rule must name the command the worker runs word for word. So the probe of T001 needs one of these. Each needs the user: an `ask` rule is a change to the user's settings, and approving a `git rebase` is outside the small-and-safe list. D29 picks the `ask` rule: the user adds and removes it by hand, and no agent changes a settings file.
- Rationale: the orchestrator must not write into a worker's approve channel (D28).
- Alternatives considered: a write to a protected path (`.claude/`, `.git/`): it prompts, but `edit_ok` refuses those paths, so no request is written. A commit with `--amend`: the git guard asks, but `commit_check` drops it on the flag (`hooks/st-approve.py:244-253`).

### R2. The monitor is a background subagent, `stratum:st-monitor`

- Decision: one new agent file `agents/st-monitor.md`, `model: opus`, `tools: Read, Bash, Write`. The main session starts one per pane worker with the Agent tool, in the background (the default). It runs `scripts/st-worker.sh wait` in a loop and ends its run only with `finished`, `stopped`, `gone` or `needs you`.
- Rationale: a background subagent lets the main session go on while each monitor waits, so two monitors act at the same time (SC-002). Read, Bash and Write are kept by a background subagent. Write is needed only for the Codex views file of FR-028 (R8). The model is set the same way as for every Stratum agent: the `model:` line, and `.stratum/models.json` through `hooks/st-models.py` (FR-024). `hooks/st-models.py:8` builds its agent list from `agents/`, so it needs no change.
- Alternatives considered: foreground subagents: the main turn waits for all of them, so a `needs you` of one waits for the others. `watch --roster` in the main session: it is what FR-004 removes.

### R3. Every answer is tied to its screen (FR-007)

- Decision: `wait` and `watch` print a `screen <hash>` line for an open work question too, not only for a permission dialog (`scripts/st-worker.sh:168`). `answer --screen <hash>` checks that hash for a work question as it does for a dialog (`:531-533`). The question hash covers a fixed block that ends at the question's `Enter to select` line (or the numbered options after `Ready to submit your answers?`), so a status line below it does not change it. With `--screen` left out, `answer` works as today, so the main session's own path (the fallback of FR-022) does not change. The monitor guard (R5) refuses an `answer` from a monitor that has no `--screen`.
- Rationale: a late answer can then not reach a newer question (SC-004). The check sits in the script, so a test can turn red when it is removed. Making `--screen` required for everyone would break tests A1, A3, AQ1, AQ2, R10 and R10b of `tests/test_st_worker.sh` and the pinned rows W1 and W28 of `tests/test_worker_rules.sh` for no gain in the main session.
- Today `wait` prints no `screen` line for a question, and tests AN9 (`tests/test_st_worker.sh:1793`) and WD3 (`:2048`) pin that. This decision changes it on purpose, so T005 changes those two checks.
- Alternatives considered: a hash of the whole pane: the status line can change between `wait` and `answer`, which gives false refusals. A hash of the visible pane: same problem.

### R4. The record is written by the script, in the main session's scratchpad (FR-008, FR-014)

- Decision: `answer` and `resend` take `--record <file>`, as `approve` does today (`scripts/st-worker.sh:771`), and add one line after they send. The record file changes only when an answer or an approval is recorded; the sign of life is a separate beat file (R6). The file is `<scratchpad>/monitor-<id>-<key>/record.tsv`, in the main session's scratchpad, next to the roster file. The monitor's approvals go to the same file through `approve --record`.
- Rationale: the line is written in the same process that sends, so the record holds every answer also when the monitor dies right after (SC-008). The scratchpad is outside every git work tree, so the change check of a Codex point does not see it (`scripts/common.sh:27-38`) and no project file changes. D14 (N6) already puts a monitor's notes in the scratchpad. A path under `.stratum/` would need a new data element (`tests/test_harness_model.sh` coverage-data) and an ignore line in every project.
- Alternatives considered: the monitor writes the record with the Write tool: an answer sent just before the monitor dies is lost.

### R5. Guards that a test can turn red (SC-003)

- Decision: three guards that do not depend on the model's judgement.
  1. A PreToolUse rule in `hooks/st-approve.py`, keyed on `agent_type == "stratum:st-monitor"`. It runs after `lock2`, adds denies only, and prints nothing for a call it allows, so the user's own permission rules still apply (contracts/monitor-guard.md). For that agent it allows only: `bash <plugin root>/scripts/st-worker.sh` with `wait`, `answer`, `approve`, `pass` or `resend`, as one command with no shell operator; `answer` only with `--screen` and `--record`; `resend` and `approve` only with `--record`; `wait` only with `--beat`; the Codex call of R8 in its exact form (`HERDR_ENV=0 bash <plugin root>/scripts/st-advisor.sh round decisions <folder> 1 <file>`). Every path it allows is in a monitor folder: a folder named `monitor-<id>`, outside any git work tree, that already holds the `beat` file the main session writes before each start; the folder and the file named are not symlinks themselves (a symlink in a parent folder, such as `/tmp` on macOS, is allowed), and the git work tree rule is applied to the real path. `--record` must be `record.tsv` and `--beat` must be `beat` in the folder of the same worker id; Write goes only to `spec.md` and `views-<n>.md` in a monitor folder; the Codex call takes a monitor folder and a `views-<n>.md` in it. The `beat` file is the one extra rule: a monitor cannot make a folder the main session did not prepare. It denies Read of `result.md` and `result-round<n>.md`, Grep and Glob (not in its tools line), every call on a monitor folder that another `agent_id` owns (R11), and every other Bash command. It fails closed for that agent: any error on its path through `main()`, `worker_session` and `lock2` included, gives a deny. Other agents and the main session see no change.
  2. `answer` refuses a one-time yes for a dialog whose block matches the never list of `hooks/st-approve.py` (`NEVER`, `:27-38`). It fails closed: `--never` exits 4 for "not on the list" and 0 for "on the list", and `answer` sends the yes only on exit 4. A crash, or the SIGTERM handler (`:358-360`), exits 1, and every exit but 4 refuses. Before the match it removes this plugin's own `scripts/st-lock.sh` path, the same strip `bash_ok` makes (`:153-155`): a plugin root under `~/.claude/` would else match `\.claude\b` and refuse every `[lock]` test dialog. This also holds for the main session's fallback path, where the skill already says to send no key for such a dialog (`skills/st-worker/SKILL.md:28`). `NEVER` does not hold two parts of the never list of step 6: "anything outside the worker's worktree" (`bash_ok` checks that on a command's paths, `:158-164`) and an edit of a dependency file (`edit_ok`, `:146-147`). Those two rest on the agent rule, as the gates do.
  3. The `tools:` line of `agents/st-monitor.md`: no `Skill`, no `Agent`, no `AskUserQuestion`, no `Edit`.
- Rationale: SC-003 needs a check per kind that goes red when its guard is removed. A rule in the agent text can only go red in a live run, and it may not go red at all. The orchestrator's brief says a grep of skill text alone does not prove a guard. `hooks/st-approve.py` already runs as a PreToolUse hook for Bash, Edit, Write, Read, Grep and Glob (`hooks/commands.json`), so no new hook file and no new harness element. The locks of FR-032 (`lock2` and `request`) stay as they are.
- Kinds and their guards: FR-010 (end of a worker): guard 1 (no `result`, `followup`, `close`, `git`, `gh`; no write to `tasks.md`; no Read of the result file) and guard 3 (no Skill, so no review). FR-011: guard 2, and the existing cut-off check (`scripts/st-worker.sh:544`). FR-012: a push is guard 2. A lane gate question has no script guard (F-gate below). FR-013: guard 1 (no `start`, `goal`, `autonomous-on`, `autonomous-off`). FR-014: guard 1. FR-015: guard 3 (no Skill, no Agent) and guard 1 (no other `st-advisor.sh` point). FR-016: guard 3 (no AskUserQuestion; a background subagent does not keep it either).
- F-gate: a lane gate question ("Do you agree the spec?", "OK to build?") is a work question on the screen. The monitor must relay the user's own answer to it after a `needs you` (US2-5), so a script cannot refuse every answer to it. Its guard is the agent rule only (D32, and SC-003 leaves it out). Its check is the live run in quickstart section 3 step 2, and removing the rule may not turn that run red.
- What still stops the outward effect of a wrong answer to the st-pr gate: after its gate, `/stratum:st-pr` pushes first (`git push -u origin <branch>`, `skills/st-pr/SKILL.md:83`) and opens the PR after (`:86`). The git guard asks for every plain push (`hooks/st-git-guard.py:297`), so the push shows as a dialog in the worker's pane. In autonomous build mode it does not become an approval request, because `bash_ok` refuses it on `NEVER` (`hooks/st-approve.py:28`, `:307`). On the dialog, guard 2 refuses the one-time yes, so the push and the PR wait for the user. The gate answer itself (for example a wrong title) is not stopped.
- Fails open outside its branch: guard 1 acts only when the hook input has `agent_type` equal to `stratum:st-monitor`. That value is known from the docs only (`hooks.md` line 2740). A missing or different value gives no deny and the unit tests stay green, so quickstart section 3 step 3 must pass live before the release.
- Alternatives considered: a new hook file: more harness model work for the same check. Frontmatter `hooks:` in the agent file: ignored for plugin agents (`sub-agents.md` line 235).

### R6. Sign of life and the bound (FR-021)

- Decision: the sign of life is the mtime of one file, `<scratchpad>/monitor-<id>-<key>/beat`. The main session writes it with the Write tool just before it starts or continues the monitor. `wait` learns its path from a new flag, `wait --beat <file>`, and sets its mtime at its start and at each 10 s slice. A new command `st-worker.sh stale <beat file>...` prints `stale\t<file>\t<age s>` for each beat file that is older than the bound, or missing, and exits 4, else exits 0 and prints nothing. The main session runs it in a loop with the Monitor tool (`while bash <plugin root>/scripts/st-worker.sh stale <beat files>; do sleep 60; done`, deadline 30 minutes, started again on the deadline notice and when a monitor starts or ends). On a `stale` line it stops that monitor with `TaskStop`, confirms the stop (a second `TaskStop` on the same id finds no task), writes the beat file again, then continues the same monitor with SendMessage. Only when SendMessage fails does a new `stratum:st-monitor` take the worker, with a new folder (R11: the old folder is owned by the stopped monitor's agent id).
- The write by the main session is what keeps a healthy monitor from looking stale: a new monitor has not run `wait` yet, and a monitor continued after a `needs you` has an old beat. Each monitor has its own beat file, so a restart of the watch for one monitor does not hide another.
- Why a flag and not a path taken from `--record`: `wait` has no `--record` now, and one explicit flag is the smallest form a test and the hook can check.
- The bound: 550 s (the longest script call a monitor makes outside `wait`: a headless Codex run of 540 s plus the 10 s kill, `scripts/st-advisor.sh:266-273`) plus two times the longest gap measured in T001 between two `st-worker.sh` calls of a subagent that called `advisor` in between, rounded up to a whole minute. T001 measures it, and T018 writes the number. No number is set before that.
- Rationale: the beat comes from the script the monitor runs, not from transcript size. The user's lessons say transcript size is not liveness, and to resume a dead agent rather than start a new one.
- Alternatives considered: the size or mtime of the subagent's output file: not a sign that the model loop turns. A loop inside `stale`: it cannot be tested without waiting for its bound.

### R8. Codex before a big decision (FR-028, FR-029)

- Decision (D30): the monitor runs `HERDR_ENV=0 bash <plugin root>/scripts/st-advisor.sh round decisions <monitor folder> 1 <views file>` from the project root. No new point, no usage line changes. `round` runs Codex in modes `auto`, `codex` and `both` (`scripts/st-advisor.sh:164`, `:173`); mode `off` prints `no advisor: mode off` and the decision goes up.

- Shortcut: the placeholder `spec.md` and the "talk with another advisor" wording (plan.md, Shortcuts).

- Facts that hold: in this repo the mode is `codex` (`.stratum/advisor.json`), so the `decisions` point never runs Codex (`scripts/st-advisor.sh:173`). A busy tab (exit 75), a change check that trips, and a timeout give `BLOCKED`, so the decision goes up and no queue is needed. A point writes `<folder>/advisor.md` (`:77`, `:206`, `:286`), so the folder a monitor passes must be outside the work tree. ### R11. A monitor is locked to its own worker (FR-035, D36)

- Decision (D36, the user's pick for F24, option O51): the lock is who makes the call. Every command the guard allows names a monitor folder (`--record`, `--beat`, the Write path, the round call's folder; `pass` gets `--record` for this), and the folder name holds the worker id of the same command. On a monitor call that passed every other check, the hook makes `<folder>/owner` with an exclusive create that does not follow a symlink when it is missing, and writes the hook input's `agent_id` into it; when `owner` exists, the call goes on only if it is a regular file whose content equals that `agent_id`. A call with no `agent_id` is denied, and an error on this path gives a deny. A monitor cannot write `owner`. Claude Code sets `agent_id` (`hooks.md` lines 256 and 766-771), so a monitor that knows another folder's full name still cannot use it.
- The folder name keeps its 16-character `mktemp` key. It is not the lock: it only makes the seconds before the right monitor's first call safe, because a different monitor cannot guess the name.
- A continue with SendMessage keeps the same monitor, so the same `agent_id` and `owner`. A new monitor after a stopped one gets a new folder (contracts/st-worker-skill.md C1), so no `owner` file is ever removed, and the old record file stays and is shown.
- Why: no secret has to stay secret after the first call, so the Read allow list of the earlier form is gone (it had the hole F30 found), and the rule is smaller. The first call needs no file that the main session writes later, so there is no race for the right monitor. A test turns it red (contracts/monitor-guard.md, FR-035 rows and negative controls). It works for a saved machine, because the folder is on this machine.
- Revoked folders: when the main session stops using a monitor folder, for any reason (a takeover, or a new monitor after a stopped one), it writes `<old folder>/revoked` with the Write tool, and the hook denies every monitor call on a folder that holds `revoked`, its owner's included. A monitor cannot write `revoked`. So one worker has at most one usable folder at any time, which also holds FR-003 by code.
- Given twice: the guard denies a monitor command where any of `--record`, `--beat`, `--screen`, `--machine` or `--request` appears more than one time, because `scripts/st-worker.sh` keeps the last value (`:27`) and a second value could name another folder than the one the guard checked.
- The one limit that stays, in full: the race of the first call is real. Read is allowed for any path, so a tricked monitor can find a new folder's full name in the main session's transcript (`~/.claude/projects/<project>/<session id>.jsonl`, which holds every brief) as soon as the main session starts that monitor. If it makes a call on that folder before the right monitor's first command, it owns the folder. It needs all of: an injected instruction that reaches the tricked monitor and tells it to do this, and a call in the few seconds between the new monitor's start and its first command. What stops it after that: the right monitor's first call is denied, so it ends with `needs you` and the deny text; the main session then writes `revoked` in that folder, which ends the takeover at once (every later call of the tricked monitor on it is denied), starts a monitor with a new folder, and tells the user in one line (contracts/st-worker-skill.md C1). The tricked monitor's few calls before that are in that folder's record file, which the main session shows with the others. A new folder is open to the same race again.
- Alternatives considered: (1) a secret folder name alone, with a Read allow list: the name can reach a monitor through a session transcript in a config folder that is a git work tree (F30), through the answer of the Codex round call, and through the worker's pane (F31). (2) The main session writes the agent id into the folder: the id is known only after the start, so the first call races. (3) A key file and a `--key` flag: the same secret problem as (1).
- Proved before the build, in T001: that the hook input holds an `agent_id` for a subagent's call, whether it is the id the Agent tool gives the main session, and that it stays the same after a SendMessage continue. A subagent's shell has `CLAUDE_CODE_SESSION_ID` (the main session's id), `CLAUDE_CODE_CHILD_SESSION=1` and `CLAUDE_CODE_SESSION_ATTENDED=1`, and no variable with its agent id (live test, 2026-11-26), so T001 reads the hook input through a temporary, off-by-default log block in `hooks/st-approve.py` that writes only outside the project and is removed at the end of T001 (quickstart section 1 steps 3, 6 and 10). No `agent_id`, or one that changes after a continue, stops the feature before T002. T001 writes the results under `## Probe results (T001)` at the end of this file.
- Not tested live until T013: the same facts for the shipped `stratum:st-monitor`, and that a call naming another monitor's full folder is denied. The live checks are quickstart section 3 step 5, which must pass in T013.
