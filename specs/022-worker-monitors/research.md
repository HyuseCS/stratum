## Decisions

### R1. Where an approval request comes from in a worker

- Decision: in an auto-mode worker, a request comes only from a prompt that auto mode still shows: an explicit `ask` rule, or a hook `ask`. A worker's commit is `commit: auto` (`scripts/st-worker.sh:337`), so a commit never asks. The git guard asks for `git rebase`, `git branch --force` and a few more (`hooks/st-git-guard.py:309-319`). The approve hook writes a request only when the command passes `bash_ok` or the edit passes `edit_ok` (`hooks/st-approve.py:307-316`). An `ask` rule matches the exact command text, so the rule must name the command the worker runs word for word. So the probe of T001 needs one of these. Each needs the user: an `ask` rule is a change to the user's settings, and approving a `git rebase` is outside the small-and-safe list. D29 picks the `ask` rule: the user adds and removes it by hand, and no agent changes a settings file.
- Rationale: the orchestrator must not write into a worker's approve channel (D28).
- Alternatives considered: a write to a protected path (`.claude/`, `.git/`): it prompts, but `edit_ok` refuses those paths, so no request is written. A commit with `--amend`: the git guard asks, but `commit_check` drops it on the flag (`hooks/st-approve.py:244-253`).

### R2. The monitor is a background subagent, `stratum:st-monitor`

- Decision: one new agent file `agents/st-monitor.md`, `model: opus`, `tools: Read, Bash, Write`. The main session starts one per pane worker with the Agent tool, in the background (the default). It runs `scripts/st-worker.sh wait` in a loop and ends its run only with `finished`, `stopped`, `gone` or `needs you`.
- Rationale: a background subagent lets the main session go on while each monitor waits, so two monitors act at the same time (SC-002). Read, Bash and Write are kept by a background subagent. Write is needed only for the Codex views file of FR-028 (R8). The model is set the same way as for every Stratum agent: the `model:` line, and `.stratum/models.json` through `hooks/st-models.py` (FR-024). `hooks/st-models.py:8` builds its agent list from `agents/`, so it needs no change.
- Alternatives considered: foreground subagents: the main turn waits for all of them, so a `needs you` of one waits for the others. `watch --roster` in the main session: it is what FR-004 removes.

### R3. Every answer is tied to its screen (FR-007)

- Decision: `wait` and `watch` print a `screen <hash>` line for an open work question too, not only for a permission dialog (`scripts/st-worker.sh:168`). `answer --screen <hash>` checks that hash for a work question as it does for a dialog (`:531-533`). The question hash covers a fixed block that ends at the question's `Enter to select` line (or the numbered options after `Ready to submit your answers?`), so a status line below it does not change it. With `--screen` left out, `answer` works as today, so the main session's own path (the fallback of FR-022) does not change. The monitor guard (R5) refuses an `answer` from a monitor that has no `--screen`.
- Rationale: a late answer can then not reach a newer question (SC-004). The check sits in the script, so a test can turn red when it is removed. Making `--screen` required for everyone would break tests A1, A3, AQ1, AQ2, R10 and R10b of `tests/test_st_worker.sh` and the pinned rows W1 and W28 of `tests/test_worker_rules.sh` for no gain in the main session.
- Today `wait` prints no `screen` line for a question, and tests AN9 (`tests/test_st_worker.sh:1793`) and WD3 (`:2048`) pin that. This decision changes it on purpose, so T005 changes those two checks.
- Alternatives considered: a hash of the whole pane: the status line can change between `wait` and `answer`, which gives false refusals. A hash of the visible pane: same problem.

### R4. The record is written by the script, in the main session's scratchpad (FR-008, FR-014)

- Decision: `answer` and `resend` take `--record <file>`, as `approve` does today (`scripts/st-worker.sh:771`), and add one line after they send. The record file changes only when an answer or an approval is recorded; the sign of life is a separate beat file (R6). The file is `<scratchpad>/monitor-<id>/record.tsv`, in the main session's scratchpad, next to the roster file. The monitor's approvals go to the same file through `approve --record`.
- Rationale: the line is written in the same process that sends, so the record holds every answer also when the monitor dies right after (SC-008). The scratchpad is outside every git work tree, so the change check of a Codex point does not see it (`scripts/common.sh:27-38`) and no project file changes. D14 (N6) already puts a monitor's notes in the scratchpad. A path under `.stratum/` would need a new data element (`tests/test_harness_model.sh` coverage-data) and an ignore line in every project.
- Alternatives considered: the monitor writes the record with the Write tool: an answer sent just before the monitor dies is lost.

### R5. Guards that a test can turn red (SC-003)

- Decision: three guards that do not depend on the model's judgement.
  1. A PreToolUse rule in `hooks/st-approve.py`, keyed on `agent_type == "stratum:st-monitor"`. For that agent it allows only: `bash <plugin root>/scripts/st-worker.sh` with `wait`, `answer`, `approve`, `pass` or `resend`, as one command with no shell operator; `answer` only with `--screen` and `--record`; `resend` and `approve` only with `--record`; `wait` only with `--beat`; the Codex call of R8 in its exact form (`HERDR_ENV=0 bash <plugin root>/scripts/st-advisor.sh round decisions <folder> 1 <file>`, folder and file outside any git work tree). It denies Write and Edit to any path inside a git work tree, and Read of `result.md` and `result-round<n>.md`. It denies every other Bash command. It fails closed for that agent. Other agents and the main session see no change.
  2. `answer` refuses a one-time yes for a dialog whose block matches the never list of `hooks/st-approve.py` (`NEVER`, `:27-38`). Before the match it removes this plugin's own `scripts/st-lock.sh` path, the same strip `bash_ok` makes (`:153-155`): a plugin root under `~/.claude/` would else match `\.claude\b` and refuse every `[lock]` test dialog. This also holds for the main session's fallback path, where the skill already says to send no key for such a dialog (`skills/st-worker/SKILL.md:28`). `NEVER` does not hold two parts of the never list of step 6: "anything outside the worker's worktree" (`bash_ok` checks that on a command's paths, `:158-164`) and an edit of a dependency file (`edit_ok`, `:146-147`). Those two rest on the agent rule, as the gates do.
  3. The `tools:` line of `agents/st-monitor.md`: no `Skill`, no `Agent`, no `AskUserQuestion`, no `Edit`.
- Rationale: SC-003 needs a check per kind that goes red when its guard is removed. A rule in the agent text can only go red in a live run, and it may not go red at all. The orchestrator's brief says a grep of skill text alone does not prove a guard. `hooks/st-approve.py` already runs as a PreToolUse hook for Bash, Edit, Write, Read, Grep and Glob (`hooks/commands.json`), so no new hook file and no new harness element. The locks of FR-032 (`lock2` and `request`) stay as they are.
- Kinds and their guards: FR-010 (end of a worker): guard 1 (no `result`, `followup`, `close`, `git`, `gh`; no write to `tasks.md`; no Read of the result file) and guard 3 (no Skill, so no review). FR-011: guard 2, and the existing cut-off check (`scripts/st-worker.sh:544`). FR-012: a push is guard 2. A lane gate question has no script guard (F-gate below). FR-013: guard 1 (no `start`, `goal`, `autonomous-on`, `autonomous-off`). FR-014: guard 1. FR-015: guard 3 (no Skill, no Agent) and guard 1 (no other `st-advisor.sh` point). FR-016: guard 3 (no AskUserQuestion; a background subagent does not keep it either).
- F-gate: a lane gate question ("Do you agree the spec?", "OK to build?") is a work question on the screen. The monitor must relay the user's own answer to it after a `needs you` (US2-5), so a script cannot refuse every answer to it. Its guard is the agent rule only. Its check is the live run in quickstart section 5, and removing the rule may not turn that run red.
- Fails open outside its branch: guard 1 acts only when the hook input has `agent_type` equal to `stratum:st-monitor`. That value is known from the docs only (`hooks.md` line 2740). A missing or different value gives no deny and the unit tests stay green, so quickstart section 3 step 3 must pass live before the release.
- Alternatives considered: a new hook file: more harness model work for the same check. Frontmatter `hooks:` in the agent file: ignored for plugin agents (`sub-agents.md` line 235).

### R6. Sign of life and the bound (FR-021)

- Decision: the sign of life is the mtime of one file, `<scratchpad>/monitor-<id>/beat`. The main session writes it with the Write tool just before it starts or continues the monitor. `wait` learns its path from a new flag, `wait --beat <file>`, and sets its mtime at its start and at each 10 s slice. A new command `st-worker.sh stale <beat file>...` prints `stale\t<file>\t<age s>` for each beat file that is older than the bound, or missing, and exits 4, else exits 0 and prints nothing. The main session runs it in a loop with the Monitor tool (`while bash <plugin root>/scripts/st-worker.sh stale <beat files>; do sleep 60; done`, deadline 30 minutes, started again on the deadline notice and when a monitor starts or ends). On a `stale` line it stops that monitor with `TaskStop`, confirms the stop (a second `TaskStop` on the same id finds no task), writes the beat file again, then continues the same monitor with SendMessage. Only when SendMessage fails does a new `stratum:st-monitor` take the worker, with the same folder.
- The write by the main session is what keeps a healthy monitor from looking stale: a new monitor has not run `wait` yet, and a monitor continued after a `needs you` has an old beat. Each monitor has its own beat file, so a restart of the watch for one monitor does not hide another.
- Why a flag and not a path taken from `--record`: `wait` has no `--record` now, and one explicit flag is the smallest form a test and the hook can check.
- The bound: 550 s (the longest script call a monitor makes outside `wait`: a headless Codex run of 540 s plus the 10 s kill, `scripts/st-advisor.sh:266-273`) plus two times the longest gap measured in T001 between two `st-worker.sh` calls of a subagent that called `advisor` in between, rounded up to a whole minute. T001 measures it, and T017 writes the number. No number is set before that.
- Rationale: the beat comes from the script the monitor runs, not from transcript size. The user's lessons say transcript size is not liveness, and to resume a dead agent rather than start a new one.
- Alternatives considered: the size or mtime of the subagent's output file: not a sign that the model loop turns. A loop inside `stale`: it cannot be tested without waiting for its bound.

### R7. Advice on a weaker model (FR-024, FR-025, FR-026, FR-029)

- Decision: weaker means `sonnet` and `haiku`. `opus` and `fable` are not weaker. The main session passes the monitor's model in its brief. The monitor does not name `advisor` in its tools list (research F6, F11). Before it answers a small work question on `sonnet` or `haiku`, it calls `advisor`. No `advisor` tool, a failed call, or an answer that is not a clear yes with no condition: the question goes up (D27). A permission dialog is decided by the lists only, with no advisor call (FR-026).
- Not checked: the `advisor` tool on a `sonnet` or `haiku` agent with a fixed tool list (research F6 is one run on Opus 5.5). The pairing rules say Sonnet 5.5 and Haiku 5.5 accept a Fable or Opus advisor (research F5). Quickstart section 6 checks it live.

### R8. Codex before a big decision (FR-028, FR-029)

- Decision (D30): the monitor runs `HERDR_ENV=0 bash <plugin root>/scripts/st-advisor.sh round decisions <monitor folder> 1 <views file>` from the project root. The views file holds the question, the facts, the monitor's answer, the `advisor` answer and the `Owns:` files it touches. The monitor writes a placeholder `spec.md` (the text of its task file) into its own folder with the Write tool just before its first Codex call, so no tool call is spent in a run that never reaches Codex. The monitor guard allows that write: the folder is outside every git work tree. No new point, no usage line changes. `round` runs Codex in modes `auto`, `codex` and `both` (`scripts/st-advisor.sh:164`, `:173`); mode `off` prints `no advisor: mode off` and the decision goes up.
- Rationale: no script change, and the `round` prompt ("for each open point, agree, or keep your view and give the reason", `:224`) asks Codex to agree or not with a view, which is the yes or no FR-029 needs.
- Shortcut: the placeholder `spec.md` and the "talk with another advisor" wording (plan.md, Shortcuts).
- Alternatives considered: a new point `decide` with its own prompt (rejected by the user for now; it is the upgrade path).
- Facts that hold: in this repo the mode is `codex` (`.stratum/advisor.json`), so the `decisions` point never runs Codex (`scripts/st-advisor.sh:173`). Only `APPROVED` is a clear yes: `REVISE` (also with only LOW findings), `BLOCKED`, `no advisor: ...`, `advisors: none`, a usage line or a non-zero exit all count as no agreement and the decision goes up. A busy tab (exit 75), a change check that trips, and a timeout give `BLOCKED`, so the decision goes up and no queue is needed. A point writes `<folder>/advisor.md` (`:77`, `:206`, `:286`), so the folder a monitor passes must be outside the work tree. A subagent of the main session has `HERDR_ENV=1`: in fact 2 it ran `wait` on a local worker (worktree `stratum-51_probe` on this machine) with no `--machine`, and `scripts/st-worker.sh:115` refuses that unless `HERDR_ENV` is `1`. So a Codex point from a monitor takes the tab path (`scripts/st-advisor.sh:249`) unless it is forced headless. Headless (`HERDR_ENV=0`) means it never waits on the shared Codex tab lock, never has a tab prompt to watch (D19), and ends inside 550 s (R6). T001 confirms the value (m3).
