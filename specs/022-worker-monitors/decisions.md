# Decisions: 022-worker-monitors (#51)

A line that starts with WITHDRAWN or CHANGED is history: build from the decision it names, not from its own text.

- D8 (Q7): O2. The feature changes who does the work: how the orchestrator gives work to agents and workers. The steps and gates of the lanes stay as they are. Rejected: O1 (review the steps and gates of each lane), O3 (both, as two features).
- D9 (Q8): O7, the user's own option. Add a monitoring layer. The main orchestrator starts monitor subagents and assigns each one to one summon (a worker, or a workspace that is an orchestrator itself). A monitor watches only its summon and answers its needs as the orchestrator does today; when the orchestrator is in autonomous mode it does this with no user. The main orchestrator gets only what a monitor cannot settle, so it is not overloaded when many summons run. Reason (user): one orchestrator cannot keep up when it monitors too many workers and summons. Rejected: O4 (dispatcher: one worker runs the lane for each issue), O5 (workers by default for `[P]` tasks), O6 (role changes only).
- D10 (Q9): CHANGED by D18 (b): "does for its summon what the orchestrator does today" means the monitoring part only (`skills/st-worker/SKILL.md` step 6: wait, answer, approve, pass, resend). O8, widened by the user. In normal mode a monitor settles the four kinds of events that the orchestrator settles alone today (a permission dialog on the allow list, a small and safe approval request, an unsent start prompt, a small work question that the brief or the plan settles), with the same lists, and records each answer. With autonomous mode on, a monitor does for its summon what the orchestrator does today, except merge, close and other dangerous actions. All else goes up to the main orchestrator. Goal (user): a first step to a "loop engineering" feature in the harness, so that work is faster and more efficient with no loss of quality. Rejected: O9 (permission events only), O10 (the review by the monitor in normal mode too).
- D11 (Q10): WITHDRAWN by D18 (the review part: no review runs in or for a monitor). In force from this line: only the addition, which D13 and D16 carry. O11, with an addition by the user. In autonomous mode the worker's own session runs `st-review` on its work. The monitor reads the findings from the result file, checks each one against the source, and sends the real ones back with `followup`. Addition (user, corrected after Q11): when a monitor agent runs on a weaker model, it can use the Stratum advisor, so that its decisions have input from a stronger model. The addition is about the monitor's model, not the worker's model. Q11 (when the Codex review runs for a worker on a weaker model) is withdrawn: it came from a wrong reading of this addition. Rejected: O12 (the monitor reviews the diff itself), O13 (the main orchestrator starts `st-review` and sends the findings to the monitor).
- D12 (Q13): WITHDRAWN by D18: a monitor starts no `st-review`, so its "to test in Plan" item is dropped too. O20. In autonomous mode the monitor starts the `st-review` agent itself on its worker's branch and gets the findings direct. Facts that stay true (live tests, 2026-11-26, general-purpose agents on `haiku`): a subagent can start a subagent, and the reply reaches a parent that stays alive. The feature does not use these facts.
- D13 (Q12): CHANGED by D18 (c): the clause "before it drops a finding" no longer applies, because a monitor judges no findings. CHANGED by D27: O17 is no fallback; a weaker monitor that cannot get advice first sends the question up. O18. A monitor on a weaker model calls the built-in `/advisor` before it answers a work question, so the decision has input from a stronger model first. The allow list and the never list decide the permission dialogs, with no advisor call. Each monitor records its answers (D10), and the main orchestrator can send that record to the advisors at the story review as it does today. Fact (probe, 2026-11-26): a general-purpose subagent has the `advisor` tool in a session where the user set an advisor. If a Stratum agent with a fixed tool list does not get the `advisor` tool (see Queued research), O17 is the fallback. Rejected: O17 (after the answer only, as a list), O19 (no advisor: a weaker monitor sends each work question up).
- D14 (Q14): O22, with N3 conditional (user). N6 CHANGED by D18: `followup` is the main orchestrator's job. A monitor never does these, also in autonomous mode, and each one goes up to the main orchestrator. N1: the end of a worker (result, review, follow-up, merge, PR merge, the tick in `tasks.md`, close). N2: the never list of today (push, force-push, delete a branch or a worktree, `reset --hard`, an action outside the worker's worktree, secrets and `.env`, `.claude/`, `.mcp.json`, git hooks, a new dependency, a network call to a new host, the lock files). N3: a big decision (spec, scope, approach, privacy, access, data model, contracts, an action that cannot be undone, an action that reaches an audience, a high cost); D15 sets its condition. N4: the PR gate and the push before it. N5: start and stop (no worker start, autonomous mode neither on nor off). N6: file changes (a monitor changes no file of the project and sends no `followup`; it writes only its own notes in the scratchpad). N7: talk to the user (only the main orchestrator does). Rejected: O23 (N1, N2 and N4 only).
- D15 (Q15): CHANGED by D20 (condition 2: Codex must agree too). O24. N3 is split in two. Hard part, never for a monitor: privacy, access, data model, contracts, secrets, money or a high cost, an action that cannot be undone, an action that reaches an audience. Soft part (spec, scope, approach): a monitor can settle one only when all four are true: (1) autonomous mode is on; (2) `/advisor` agrees, and the monitor calls it first, also on a strong model; (3) the effect stays inside the worker's own task files and can be undone; (4) the monitor reports it as "big decision made" and the main orchestrator shows it to the user before the merge, and the user's "no" undoes it. Rejected: O25 (by the risk level of the feature), O26 (by the user's word at the start of each run).
- D16 (Q16): O27. The default model of a monitor is `opus`. "Weaker" means `sonnet` and `haiku`: the user gets a weaker monitor only when they set one with `/stratum:st-model`, and then D13 applies. A weaker monitor with no advisor set sends each work question up to the main orchestrator. Reason: the judgment of permission dialogs has no advisor behind it, so it stays on a strong model by default, as the other judging agents have. Rejected: O28 (default `sonnet`), O29 (no model in the agent file, so the model of the main session).
- D17 (Q17): WITHDRAWN by D18 (the `st-review` loop of O30 and its report contents). In force from this line: only the addition. Addition (user, corrected after Q18): a monitor runs no Codex review loop. Review rounds with Codex (`/stratum:st-advisor`, also on a PR) are not a monitor's job and can take many rounds. The monitor keeps watching its worker through all of them, with no fixed count of rounds (D22 says how). Codex is there only to advise a monitor on its decisions. Q18 (when a Codex review loop of a monitor ends) is withdrawn: it came from a wrong reading of this addition. Rejected: O31 (two fix rounds), O32 (no limit) for the `st-review` loop.
- D18 (Q19): both advisors, and a scope rule (user). Scope rule: a monitor only monitors. Code review, plan, review and other orchestrator, builder or planner jobs are not in the monitor. This changes earlier decisions: (a) D12 and the review loop of D17 are withdrawn: a monitor starts no `st-review` and runs no fix round; result, review, follow-up, merge, tick and close stay with the main orchestrator as today (`skills/st-worker/SKILL.md` steps 7 to 11); (b) in D10, "does for its summon what the orchestrator does today" means the monitoring part only (step 6: wait, answer, approve, pass, resend); (c) in D13 the part about dropped findings no longer applies; (d) a monitor reports the end state of its worker and its record to the main orchestrator. Advisors (user: "both, but codex should only review or give advice when the monitor asks codex for advice for big decisions"): the built-in `/advisor` and Codex are both in the design. Codex advises only when a monitor asks it about a big decision (the soft part of N3, D15), and it does no review for a monitor. How the two combine at a big decision is D20. Rejected: O36 alone (only `/advisor`), O37 as written (Codex for each decision), O38 (by the risk table).
- D19 (Q20): O39. A pane worker gets one monitor, for the two kinds: a worker on one task, and a worker on a whole issue (which can run a lane and opens its own PR). A headless worker gets none, because it has no pane and no dialog. A Codex tab gets none: the session that starts a Codex point watches its own tab as today, and the main session keeps the Codex tabs that the user starts. Rejected: O40 (the monitor also watches its worker's Codex tab), O41 (one monitor for each Codex tab that the main session manages; a possible next feature).

## Proposed by the orchestrator, confirmed by the user on 2026-11-26

The user said yes to D20 to D27 after the Codex review of this file (`.stratum/advisor/stratum-51.md`, verdict REVISE with three MEDIUM findings: F4, F5, F6).

- D20: a big decision needs both advisors: condition 2 of D15 becomes "`/advisor` agrees and Codex agrees". With no Codex verdict (Codex is off or not found, the point prints `advisors: none` or a `no advisor` line, or the point is `BLOCKED`), the big decision goes up to the main orchestrator.
- D21: a monitor never passes a gate of a lane that its worker runs: "Do you agree the spec?", the open decisions of Plan, "OK to build?", the Design gate, the PR gate. Each gate question goes up to the user. From D8 (the gates stay) and the user's note of 2026-11-08 (spec, Plan and Inspect decisions go to the user). The soft part of N3 is no licence to answer a gate.
- D22: one monitor run covers one round of its worker: from `start` or `followup` until the worker is `finished`, `stopped` or `gone`, or until the monitor needs the main orchestrator. The worker's brief and `/goal` do not change (D8). For each `followup` round, also a fix round after a PR review, the main orchestrator starts the same monitor again. A monitor has no round limit of its own.
- D23: each pane worker gets one monitor, in normal mode and in autonomous mode, also when there is one worker. If a monitor cannot start, the main orchestrator watches that worker with `wait` as today, and tells the user in one line that this worker has no monitor. Changed after the Codex review (F6): this fallback puts pane text back in the main session, so it is a degraded mode that must be visible and tested, never silent.
- D24: a monitor ends a run only with a named end state: `finished`, `stopped`, `gone` or `needs you` (with the exact question). The main orchestrator starts the same monitor again when a report names no end state, and after each answer to a `needs you`. Each report carries the answers the monitor gave and the "big decision made" list so far, because for a worker on a whole issue the PR gate comes before the end. Added after the Codex review (F5): (a) a monitor that hangs or dies gives no report, so the main orchestrator must detect a monitor with no sign of life inside a bound; Plan sets the mechanism and measures the bound. (b) One worker has at most one monitor at any time: before a different monitor takes a worker, the main orchestrator stops the old one and confirms that it stopped. (c) An answer to a work question is bound to the screen it answers, as a permission answer is today (`scripts/st-worker.sh:531-533`); today `answer --keys` and `answer --text` for a work question have no such check (`scripts/st-worker.sh:546-557`), so a late answer could go to a newer question. (d) A monitor keeps its answer record in a file, so the record survives a monitor that dies.
- D25: the rule "write no monitor agent of your own" (`skills/st-worker/SKILL.md:26`) becomes: watch a pane worker only through the shipped `st-monitor` agent, and write no monitor brief of your own. `watch --roster` stays in the script as the fallback of D23.
- D26: done criteria. (1) A negative control: a monitor refuses each kind of never-list action, shown by a check that goes red when the guard is removed. (2) A count: in a live run with two or more pane workers, the main session answered zero worker dialogs. (3) The first Plan task is a live probe with a real worker: `st-worker.sh answer` and `approve` from a subagent run with no prompt to the user. Only `st-worker.sh list` was tested from a subagent (2026-11-26). If the probe fails, the main orchestrator watches as today and the feature stops for a new decision. Added after the Codex review: (4) the fallback path of D23 has its own check: with a monitor that cannot start, the main session watches the worker and tells the user. (5) A late answer does not go to a newer question, shown by a check that goes red when the screen binding of D24 (c) is removed.
- D27: a weaker monitor that cannot get advice before its answer sends the work question up to the main orchestrator. This is so when the `advisor` tool is not in its tool list, when no advisor is set, and when the call fails. It replaces the O17 fallback of D13, which let a weaker monitor answer first with no advice. From the Codex review (F4): the O17 fallback and the rule of D16 did not agree.

## Inspect phase

- D33 (orchestrator, Inspect, 2026-11-26, shown to the user at the build gate): the record files of monitors cover one session. When a session ends while workers still run, the main orchestrator shows each monitor's record file so far before the handoff. A new session that takes over the workers starts new monitors with new record files and says in one line that the earlier records were shown by the earlier session. This changes the wording of FR-009, SC-008 and one edge case line in spec.md. Reason: the record files are in the session's scratchpad (D14, N6), which a new session cannot read. Rejected: a fixed folder outside the scratchpad for monitor files, which goes against D14 (N6).
- D34 (orchestrator, Inspect, 2026-11-26, shown to the user at the build gate): SC-003 in spec.md leaves out the gate part of FR-012 and names its check: the agent rule, and the live check of quickstart section 3 step 2. This follows D32, where the user accepted that a gate question has no script guard. The outward effect of a wrong answer to a PR gate is still stopped by code: the push comes as a dialog, and the never check refuses the yes (research.md R5). The other option, which the user can still pick at the gate: the main session sends the user's gate answers itself, and the script refuses a monitor's answer to a question that matches a list of gate phrases.
- D35 (orchestrator, Inspect, 2026-11-26): the three safety findings of the first Inspect run are fixed in the plan. The monitor rule in the hook runs after `lock2`, only adds denies and prints nothing for an allowed call. The never check fails closed: `answer` sends a one-time yes only on the one exit code that means "clean". A monitor can write only `record.tsv`, `beat`, `spec.md` and `views-<n>.md` inside a `monitor-<id>` folder that the main session prepared, with no symlink.

- D36 (Q23, user, Inspect, 2026-11-26): O51. A monitor is locked to its own worker by code. The guard must deny a command that a monitor runs for a worker that is not its own, so that a monitor that follows a false instruction in pane text cannot act on a different worker of the same session. This closes Inspect finding F24. The mechanism is the plan's to pick: the smallest one that has no race at the start of a monitor and that a test can turn red. Rejected: O50 (accept it as a known limit and write it down).

- D37 (orchestrator, Inspect, 2026-11-26, shown to the user at the build gate): the mechanism of D36, after three more Inspect runs. The lock is who makes the call: at a monitor's first command the hook writes the `agent_id` of the hook input into `<folder>/owner`, and after that it allows a command for that folder only from that `agent_id`. The folder name keeps a random key from `mktemp`, which is not the lock: it only keeps the name hard to guess before the first command. The main session writes `<folder>/revoked` when it stops using a folder, and the hook denies each call for a revoked folder, so one worker has one usable folder at a time. A new monitor after a stopped one gets a new folder, so no `owner` is ever removed. A flag given two times is denied. Rejected: a lock that rests on a secret folder name with a Read allow list (Inspect broke it: the name leaks through a session transcript in a config folder that is a git work tree, through the answer of the Codex round call and through the worker's pane); the agent id written by the main session before the first command (the id is known only after the start, so the first command would wait on the main session).
- D38 (orchestrator, Inspect, 2026-11-26, shown to the user at the build gate): from Codex plan round 5, one MEDIUM finding. Taken: T001 also checks, before any lock code is built, that the hook input holds an `agent_id` for a subagent's call and that it stays the same after a continue with SendMessage, with a stop rule. For that, T001 adds one temporary block to `hooks/st-approve.py` that writes five fields of the hook input to a file outside the project, only while a probe file says `on`, and T001 removes the block and checks that it is gone. Not taken: the main session writes the owner and the monitor's first command waits for it, because the start of each monitor would then wait on the main session, which is the part that gets overloaded. It is in plan.md, Shortcuts, with its trigger.
