# Contract: `.c4` text format

The test reads the model with grep and a small parser, with no `npx` (FR-013). So the text has one
fixed shape. LikeC4 accepts more shapes than this. The test accepts only this one. Ids, kinds and
titles are fixed in [data-model.md](../data-model.md).

## Files

| Path | Holds |
|------|-------|
| `docs/harness/likec4.config.json` | `{"name": "stratum-harness", "title": "Stratum harness"}` and nothing else. |
| `docs/harness/model/*.c4` | `specification` and `model` blocks only. |
| `docs/harness/views/*.c4` | `views` blocks only. |
| `docs/harness/.likec4/*.likec4.snap` | Dragged layouts, written by the VS Code preview only. |
| `docs/harness/README.md` | Generated page. Never edited by hand. |
| `docs/harness/atlas/data.mjs` | The atlas source (US5). The only atlas file edited by hand. |
| `docs/harness/atlas/atlas.html`, `docs/harness/atlas/SYSTEM.md` | Generated by the build line of spec.md FR-015, which runs the installed skill's `build.mjs` and `template.html` in a temp folder (`META.outDir` is `'.'`). Never edited by hand. The skill's `build.mjs` and `template.html` are not in the repo (D17). |

No other file goes in `docs/harness/`. The atlas folder holds no `.c4` file, so LikeC4 reads
nothing in it. Indent with 2 spaces. No backtick anywhere in a `.c4` file.
No `<` or `>` in a title, summary or label. For an apostrophe use `\'` or a double-quoted string.

## Specification (`model/0-spec.c4` only)

```c4
specification {
  element group
  element actor
  element event
  element skill
  element agent
  element hook
  element statusline
  element script
  element procedure
  element pluginfile
  element datafile
  relationship starts
  relationship reads
  relationship writes
  relationship runs
  relationship passes
  tag vendored
}
```

Exactly these element kinds, relationship kinds and the one tag, one per line. No lane tags (D12). No `style` blocks: the Mermaid
export ignores them (research R5).

## Element block

```c4
model {
  extend skills {
    st-plan = skill '/st-plan' {
      summary 'Full-lane Plan phase. Starts the st-plan agent and asks the user its open decisions.'
      metadata {
        path 'skills/st-plan'
      }
    }
  }
}
```

- The declaration line is `<name> = <kind> '<title>' {`, the name being the last part of the
  registry id. Groups and actors are declared at the top level of `model` in `0-spec.c4`. Every
  other element is inside `extend <group> {`.
- A vendored skill has `#vendored` as the first line inside its block.
- `summary '<text>'` is one line: 1 to 200 characters, at most 2 sentences (a sentence ends with
  `.`, `!` or `?` then a space or the end). No abbreviations with a dot (`e.g.`).
- `metadata { path '<repo path>' }` for skill, agent, hook, statusline, script, procedure and
  pluginfile elements. `metadata { data '<run-time path>' }` for datafile elements. None for group,
  actor and event elements. Write `metadata {`, the key line and `}` on three lines.
- Every element, groups and actors too, has a block with a summary.

## Relationship line

```c4
  skills.st-plan -[starts]-> agents.st-plan 'plugin root, project root, feature dir'
```

- One relationship per line, inside a `model` block, anywhere in `model/*.c4`.
- Pattern: `<source id> -[<kind>]-> <target id> '<label>'`, with nothing after the label. No tags
  on links (D12).
  Ids are fully qualified (`skills.st-plan`, not `st-plan`). Actor ids are bare (`user`).
- Every line in `model/*.c4` that has `->` follows this pattern. A plain `->` with no kind fails.
- The label names the data: `writes` names what is written (`phase and lane`), `reads` names what
  is read, `passes` names what is handed over (`gate: you agree the spec` is a lane step, not a
  model label), `starts` names what the started agent gets, `runs` names the arguments or the event
  matcher.
- Which lanes use a link is only in the lane views (D12). An LLM finds a skill's lanes and phases
  by searching `views/1-full.c4` to `views/4-design.c4` for its id.

## Lane views (dynamic)

Each lane keeps its own file. `views/1-full.c4` holds the Full overview and its 5 phase views,
`views/4-design.c4` holds the Design overview and its 3 mode views, `views/2-fast.c4` and
`views/3-quick.c4` hold one view each (D13). The view ids, titles, order and gate floors are in
the data-model view table. The first view in each lane file is the lane id (`full`, `fast`,
`quick`, `design`).

```c4
views {
  dynamic view full {
    title 'Full lane'
    include skills.st-define with { navigateTo full-define }
    user -> skills.st '(1) task in plain words'
    skills.st -> user '(2) lane and risk line'
    skills.st -> skills.st-define '(3) feature description' { navigateTo full-define }
    skills.st-define -> user '(4) gate: you agree the spec'
  }
  dynamic view full-define {
    title 'Full lane: Define'
    skills.st -> skills.st-define '(1) feature description'
    skills.st-define -> skills.st-grill '(2) feature description'
  }
}
```

- View id and title from the data-model view table, in its order inside the file.
- Each step is one line: `<source id> -> <target id> '(n) <data>'`, or with a kind
  `-[passes]->`, and an optional ` { navigateTo <view id> }` at the end of the same line. In each
  view, `n` is 1 for the first step and goes up by 1 on each step line. `parallel { }` blocks are
  allowed. Their steps are numbered the same way.
- A gate step: `'(n) gate: <what the user must say>'`.
- Full overview: one `include skills.<phase> with { navigateTo full-<phase> }` line per phase skill
  (`st-define`, `st-plan`, `st-inspect`, `st-build`, `st-close`), so each box opens its phase view,
  and the step that starts the phase carries the same `{ navigateTo ... }`. The overview has about
  10 steps: the lane line, the start of each phase and the 4 gates.
- Design overview: the start steps (task, tool check, design file check, mode line), then for each
  mode its first step with `{ navigateTo design-<mode> }` and its gate or OK step. All three modes
  run in `skills.st-design`, so the click is on the step, not on a box.
- A phase or mode view starts at the step that starts it in the overview, renumbered from `(1)`,
  and keeps the source order. Its gate step stays where the source has it.
- `include` lines carry one element and one `navigateTo` on one line. Other `include` lines are
  not used in lane views.
- A step may have no model relationship. Draw only what the lane's skill text says, in its order.
- Clicks work only in the LikeC4 preview. The Mermaid page shows every view one after another.

## Topic views

```c4
views {
  view agents {
    title 'Agents'
    include agents.*, skills.* -> agents.*, agents.* -> skills.*, agents.* -> agents.*, agents.* -> user
  }
}
```

- `include` terms name groups one by one (`skills.* -> data.*`). `* -> x.*` collapses sources to
  their groups (research R5).
- `harness`: `events.*`, `hooks.*`, `statusline.*`, `claude`, `scripts.st-advisor-sh`,
  `scripts.st-codex-agent-sh`, `codex`, `advisor`, `stratum.state-json` (risk level),
  `stratum.advisor-json`, and the links between them.
- `dataflow`: `stratum.*`, `feature.*`, `project.*`, and the links into and out of them from
  `skills.*`, `agents.*`, `hooks.*`, `scripts.*`, `procedures.*`, `statusline.*`. If GitHub
  cannot draw it (research R8), split it into `dataflow` (`.stratum` files) and `dataflow-feature`
  (feature and project files). That makes 16 views. The test and the page heading list then
  change in the same commit.
