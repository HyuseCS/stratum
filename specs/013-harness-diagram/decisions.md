# Decisions: 013-harness-diagram (#78)

- D1 (Q1): O3, LikeC4. One text model of the harness gives many views; drag layout is saved in the source; its MCP server lets the LLM query the model. Rejected: O1 Mermaid (no saved positions, one diagram per view), O2 FigCraft (LLM reads it only through MCP while the app runs, GitHub cannot show it).
- D2 (Q2): O4. Source is `docs/harness/*.c4`; `likec4 export markdown` writes `docs/harness/README.md` with one Mermaid block per view, committed and linked from the main README. GitHub shows auto layout; the dragged layout shows only in VS Code and the LikeC4 preview. Rejected: O5 PNG export (needs Playwright and Chromium, binary churn).
- D3 (Q3): O6, complete detail. The model holds every skill, agent, hook, script and data file in the repo, each with a description and every `starts`, `reads`, `writes` and `runs` link. Views: one per lane (Full, Fast, Quick, Design), agents, harness (hooks, statusline, advisors), data flow. Rejected: O7 (issue scope only; leaves about 25 skills out).
- D4 (Q4): O8. `tests/test_harness_model.sh` checks (1) every `skills/*`, `agents/*.md`, hook and `scripts/*.sh` is in the model and the model names no missing file, (2) `likec4 validate` passes, (3) a fresh `likec4 export markdown` gives no diff on `docs/harness/README.md`. Checks 2 and 3 print SKIP when `npx` is missing. Rejected: O9 (no test, silent drift).
- D5 (Q5): O10, low key. The model shows only what exists. Gaps seen while building go in the Close gap report `specs/013-harness-diagram/gaps.md`, each with a cite. The gap report is a side note: short, not linked from the README or the diagram, not a deliverable of the feature. Rejected: O11 (gaps marked inside the model).
- D6 (Q6): O14. No `.mcp.json` in the repo: the marketplace source is `./`, so a root `.mcp.json` would load as a plugin MCP server for every user. The main `README.md` has the edit notes (changed in Define: `docs/harness/README.md` is generated and says "Do not edit manually") with the one-time command `claude mcp add --scope user likec4 -- npx -y @likec4/mcp@1.60.0`. The LLM can also read the `.c4` text or run `npx likec4 export json`. Rejected: O12 (committed root `.mcp.json`, ships with the plugin), O13 (local scope per worktree path), O15 (no MCP).
- D7 (Q7): O18. One element per skill, agent, hook, script and data file, each with a short plain `summary` (1 to 2 sentences). Each relationship's label names the data it carries. One dynamic view per lane lists, in order, who passes what to whom. No elements for steps inside a skill. Lane views list their steps by hand (a tag filter alone drew an empty view in the spike). Rejected: O16 (step elements for agent starts and file touches), O17 (every numbered step).
- D8 (Q8): O19. Each lane-view step label starts with a hand-written step number `(n)`, for example `(4) gate: you agree the spec`; the gate rule in FR-005 becomes "`gate:` after the step number". The Mermaid export shows no order of its own. Rejected: O20 (no numbers, order only from layout). Confirmed by the user.
- D9 (Q9): O21. Keep `likec4@1.60.0`, which needs Node 22.22.3 or later. The README names the Node floor. The test prints SKIP for the validate and rebuild checks when `node` is below 22.22.3, the same as when `npx` is missing. The spec assumption "Node 18 or later" becomes "Node 22.22.3 or later". Rejected: O22 (find an older LikeC4 for Node 18 and run the spike again). Confirmed by the user: the laptop has the same Node as the PC (24.14.1).
- D10 (Q10): O23. Files outside the FR-002 list that a link needs (`DESIGN.md`, `graphify-out/GRAPH_REPORT.md`, `AGENTS.md`, `CLAUDE.md`, `.claude/settings.json`, `templates/*`, `.claude-plugin/plugin.json`, `vendor.lock`, `workflows/pr.js`) get one element each. The test checks that each such plugin file exists; the coverage check does not require them. Rejected: O24 (FR-002 list only, label names the file, no target). Confirmed by the user.
- D11 (Q11, Inspect F5): O25. Pin only the top package `likec4@1.60.0`; its transitive `^` ranges resolve again per machine with `npx -y`. Accept the risk and state it in the plan's security note: dev-only tool, never shipped to plugin users, and the drift test catches a page that comes out different. Rejected: O26 (package.json and lockfile in `docs/harness/`, an npm project that ships with the plugin).
- D12 (Q12, Inspect F6): O27. Links carry no lane tags. The lane views are the one source for which steps each lane has. Rejected: O28 (keep tags and add a tag-versus-view check to T011).
- D13 (Q13, Build, after the user saw the Full view in the VS Code preview): O31. Split the big lane views with click-through. Full lane: one overview view (st, Define, Plan, Inspect, Build, Close and the 4 gates, about 10 steps) where each phase box has `navigateTo` its phase view; 5 phase views, each numbered from (1). Design lane: one overview view (start steps and the 3 modes) where each mode opens its mode view; 3 mode views. Fast and Quick stay one view each. The page grows from 7 to 15 diagrams; GitHub shows them without clicks. The test checks per-view numbering and gates, and that each `navigateTo` target exists, with new negative controls. FR-005, SC-006 and quickstart change. Runs as new tasks after T019 and T020, before Close. Rejected: O29's alternative O30 (tidy by hand), O32 (click-through with no link test). Spike: `navigateTo` on a dynamic-view step and on `include <element> with { navigateTo <view> }` both validate in likec4 1.60.0.
- D14 (Q14, Build, after the user ran /system-atlas): O34. Add a system atlas (the system-atlas skill: one `data.mjs` builds an interactive isometric `atlas.html` and a text twin `SYSTEM.md`) to this feature as a fifth user story before Close, so the user can compare it with the LikeC4 views. Rejected: O33 (atlas as its own feature after #78).
- D15 (Q15): O35. The atlas lives in-tree at `docs/harness/atlas/` (`data.mjs`, `build.mjs`, `template.html`, generated `atlas.html` and `SYSTEM.md`) and is published as a private claude.ai artifact with one stable URL. No drift test while it is a trial; add one if the atlas wins. Rejected: O36 (git-ignored scratch folder only).
- D16 (Q16): O37. The 13 gaps of `gaps.md` become the atlas's open questions (`Q-<code><n>`), each on the structure it touches, shown only in the questions tab and the index counts, not drawn on the map. The LikeC4 model stays facts only (D5). Rejected: O38 (no questions in the atlas).
- D17 (Q17): O39. The skill's `template.html` and `build.mjs` have no license and this repo is public and ships as the plugin, so they are not committed. The repo holds only `docs/harness/atlas/data.mjs` and the built `atlas.html` and `SYSTEM.md` (META.outDir '.'). `build.mjs` imports `./data.mjs` from its own folder, so the build copies the skill's two files and the repo's `data.mjs` into a temp folder, runs it there, and copies the two outputs back. The rebuild works only where the skill is installed (the user's PC and laptop). Rejected: O40 (commit all 5 files).
- D18 (Q18): O41. The private atlas URL stays out of the repo (`META.artifactUrl: ''`); it lives in the session handoff and project memory. Rejected: O42 (commit the URL in data.mjs and SYSTEM.md).
