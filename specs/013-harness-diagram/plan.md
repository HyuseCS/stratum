## Summary

Add a LikeC4 model of the whole harness in `docs/harness/`: one element per skill, agent, hook
file, script, statusline file, procedure and data file, each with a short summary, and one
relationship per link with a kind and a data label. Fifteen views (D13): twelve dynamic lane
views that list their steps by hand (a Full overview and its 5 phase views, a Design overview and
its 3 mode views, Fast, Quick), and three topic views (agents, harness, data flow). In the LikeC4
preview, a phase or mode in an overview opens its view (`navigateTo`). GitHub shows all views one
after another, with no clicks. `likec4 export markdown` makes `docs/harness/README.md`, one Mermaid block per view, which
GitHub draws. The main `README.md` links the page and says how to edit, check and rebuild it, and
how to add the LikeC4 MCP server once per machine. `tests/test_harness_model.sh` checks coverage
both ways with grep (no `npx` needed), and model validity and page rebuild with
`npx -y likec4@1.60.0` (top package pinned, D11). No skill, agent, hook or script changes (FR-014).

## Security and risk notes

Tasks that touch an external service: T001 (the test runs `npx`), T002, T018 and T020 (they run
`npx` directly), and T012 (the main `README.md` MCP note).
No task touches access rules, sign-in, an app data model, contracts of a running service, secrets,
or personal data.

- **npm registry (D11).** `npx -y likec4@1.60.0` downloads and runs third-party code at test time.
  Only the top package is pinned, in one variable in the test and in the README commands (FR-011).
  Its dependencies use `^` ranges (for example `vite ^8.3.4`, `chokidar ^5.0.0`), so `npx -y`
  resolves them again on each machine and runs their install scripts. This is a developer-only
  tool: nothing of it ships to plugin users. The `rebuild` check catches a page that comes out
  different. No `package.json` and no lockfile in the repo. The first run needs the network.
  Nothing from the repo is sent anywhere.
- **User-scope MCP server.** `claude mcp add --scope user likec4 -- npx -y @likec4/mcp@1.60.0` makes
  Claude Code start the server in every project the user opens, not only this repo. It runs
  third-party code at session start and reads `.c4` files under the session folder. The README must
  say this in one line, so the user chooses it knowingly. It is a command the user runs, never one
  the repo or the plugin runs (FR-012, D6).
- **Plugin surface.** The whole repo ships as the plugin. `docs/harness/` is not a plugin component
  folder. The test checks that no root `.mcp.json` exists and that `.claude-plugin/plugin.json` does
  not name `likec4`.
- **Model honesty.** The model says what the harness does today (FR-014). A wrong link gives the LLM
  a wrong answer with no alert, and the test checks coverage only, not link truth (spec edge case).
  Each model task writes a link only from the source text it read. T011 checks a sample of links
  against the source.

## System atlas (US5)

- **Source and build (D17).** The repo holds 3 files: `data.mjs` (the only edited file) and the
  built `atlas.html` and `SYSTEM.md`. The skill's `build.mjs` and `template.html` have no license
  and the repo is public and ships as the plugin, so they are not committed. `build.mjs` imports
  `./data.mjs` from its own folder, so the build copies the three inputs into a temp folder, runs
  there, and copies the two outputs back:
  `t=$(mktemp -d) && cp ~/.claude/skills/system-atlas/assets/build.mjs ~/.claude/skills/system-atlas/assets/template.html docs/harness/atlas/data.mjs "$t" && node "$t/build.mjs" && cp "$t/atlas.html" "$t/SYSTEM.md" docs/harness/atlas/ && rm -rf "$t"`.
  It needs only Node (no npm package) and the system-atlas skill installed at
  `~/.claude/skills/system-atlas` on that machine (the user's PC and laptop). Reading the atlas
  needs neither.
- **Paths.** By default `build.mjs` writes to the parent of its folder (`join(here, '..')`). In
  the temp build that is outside the temp folder. `META.outDir: '.'` keeps both outputs in the
  temp folder (probed in a scratch copy of the skill assets). The `nomcp` allow list gets exactly
  the 3 atlas files (FR-021). The atlas folder has no `.c4` file, so `likec4 validate` and
  `export markdown` ignore it, and the `rebuild` check still diffs only `docs/harness/README.md`.
- **No ADRs and no `CONTEXT.md`.** The skill pairs the atlas with a glossary and ADRs.
  `decisions.md` is already the decision record (D1 to D19), and the atlas needs no glossary
  (YAGNI). `DECISIONS` in `data.mjs` cites `decisions.md Dn` in the ADR column. No atlas
  `README.md` either: `SYSTEM.md` has the maintenance footer, and `docs/harness/README.md` is the
  generated LikeC4 page.
- **Drift check** (D19 replaces the "no drift test" of D15). The `atlas` check in
  `tests/test_harness_model.sh` (FR-022, test-contract.md) reads `data.mjs` with `node` and fails
  when a structure names a LikeC4 element or view id the model does not have, or a harness file
  (skill, agent, hook, statusline file, script, procedure) is in no structure or in two. It
  prints SKIP when `node` is missing, as `validate` does for `npx`. It does not rebuild the atlas,
  because the build needs the unlicensed skill (D17). The one-time checks of quickstart.md section 9
  (chapter rule, fields, 13 questions) stay as checks by hand.
- **Questions** (D16): the 13 gaps of `gaps.md` go in `cond` of the structure each touches
  (data-model.md "Gap questions"). The LikeC4 model does not change.
- **Main `README.md`** (D19, FR-023): the Harness diagram section points to the atlas first, opened
  locally from `docs/harness/atlas/atlas.html`, with the build line and the skill it needs. Then
  it points to the LikeC4 page as the detailed, checked model for the LLM (650 links, drift test,
  MCP). The `readme` check gets the atlas lines. The private claude.ai URL stays out of the README
  (D18).
- **Security.** The atlas page loads IBM Plex Mono from Google Fonts when it opens (the font
  request reaches Google). The artifact is private on claude.ai, and the orchestrator publishes it
  (FR-020). Its URL stays out of the public repo: `META.artifactUrl` is `''`, and the URL lives in
  the session handoff and project memory (D18). The 3 atlas files are in the public repo and ship
  with the plugin, like the rest of `docs/harness/`. Claude Code loads nothing from `docs/` (FR-012
  holds). The skill's unlicensed `build.mjs` and `template.html` are not committed (D17), though
  `atlas.html` holds the template's markup and script as built output.

## Work split

the model tasks (US2) and the view tasks (US1) all run at the same time after T002. Only the
integration task T018 needs all of them: it runs `likec4 validate` and makes the page. A per-task
test cannot run `validate`, because links point into files that other tasks write. Per-task tests
use the checks that read one file at a time (`summaries`, `links`, `missing`, `vendored`, `views`).

US5 work (T029 to T032): T029 (the `nomcp` allow list, test first), then T030 writes `data.mjs`

T032 is the check by hand with the user. D19 work: T033 (test first: the `atlas` check, red by a

lines of the `readme` check, then the README section, atlas first; owns `README.md` and the test)
and T035 (the D19 row in `data.mjs`, rebuild, the orchestrator republishes; owns the 3 atlas
files). T035 is not in the D19 request but follows from it: the atlas's decisions table would
otherwise still say "no drift test while it is a trial".

D13 work (T024 to T028): the test changes first and fails on the unsplit files. Then the Full
