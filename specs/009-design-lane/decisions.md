# Decisions: 009 Design lane (#49)

From the #49 discussion, 2026-10-24:

- D1: Keep `st-impeccable` as is. Its job in Stratum is the audit, not the build.
- D2: A new look comes from hallmark. Continuing an existing look comes from the project's design file (`st-impeccable document` or `st-ui-ux --persist`). `st-ui-ux` stays for stack and accessibility rules.
- D3: A separate Design lane, not a step inside Fast and Full. Rejected: a design step inside Fast and Full.

Grill:
- D4 (Q5): O3. The Design lane stops at a direction the user approves: it writes the project's design file (`DESIGN.md`) and builds one reference screen, then the rest is built in Fast or Full and follows the design file. Plus an autonomous mode: the user asks for a new page that keeps the existing direction, the lane builds it with no gate in the middle, and the user checks it after. The result must still be unique, not generic, and with good UX. Rejected: O4, the lane builds every screen end to end.
- D5 (#49 Q2): Keep hallmark (D2 stands). Vendor it the same way as impeccable: pinned in `vendor.lock`, updates from upstream through the monthly `st-sync`. Rejected: an outside plugin.
- D6 (Q6): O5. Before the autonomous mode gives the page to the user, it must pass hallmark's checks and `st-impeccable` audit and critique, with up to 2 fix rounds, then report screenshots and found, fixed and open items. Each concern has one owner, with no overlap: hallmark `sloplint` owns generic patterns in the code; hallmark's render check owns layout at each width; `st-impeccable audit` owns accessibility and speed; `st-impeccable critique` owns UX. Do not run the duplicates (`impeccable detect`, hallmark's own reviewer, the responsive part of the audit). The plan confirms this split against the real tools. Rejected: O6, only hallmark's checks.
- D7 (Q7): O7 with a vague-request check. New look: the orchestrator asks the hallmark questions once in the main session, and the answers go into the design file. Autonomous mode: the answers come from the design file and the request. If the request is vague (the page's job, its visitor or its main action cannot be found in the request or the design file), the orchestrator asks once, before the build, with all the missing items in one message. After that it builds with no more questions, and the report lists every answer it assumed. Rejected: O8, never ask.
- D8 (Q8): O9. Taste-skill is not added for now. If hallmark's output is not good enough, try taste-skill in its place. So the lane names hallmark in one place only, and a swap changes that one place. Rejected: O10, taste-skill as a second engine.
- D9 (Q9): O11. A new row in the `/stratum:st` lane table: a new look, or a new page or screen, goes to the Design lane. Changes to existing screens stay in Fast or Quick. The user can also call `/stratum:st-design` directly and can override the pick. Rejected: O12, user-call only.
- D10 (Q10): O13. This feature does not change Fast or Full. Wiring them to call the Design lane for a new-screen task goes into the workflow overhaul (#51). Until then the user calls `/stratum:st-design` for a new screen inside a bigger feature. Rejected: O14, wire it now.
- D11 (Q11, revised): O15. In autonomous mode with no design file, the lane first runs `st-impeccable document` in scan mode: it reads the look from the existing code, then asks the user what they want the look to be (mood, aesthetic, visual anti-references; at most 2 rounds of 3 questions, `reference/document.md` step 3) and has them confirm the file. Then it builds as usual. This is the only case where autonomous mode stops for the look, and it happens once per project. Rejected: O16, stop and move to the new-look mode.
- D12 (O19 vs O20): A mix. The design file is made with the `st-grill` method (one question at a time, each with a recommended answer, a design tree, until the frontier is empty). The first branches are the five `st-impeccable document` topics (North Star, overview voice, color character, elevation, components) plus UX (density, how a user moves through the screens). The grill lives in the Design lane, not in the vendored impeccable files (D1). The answers then go to `st-impeccable document`, which writes `DESIGN.md` in its own format and runs its confirm step. Rejected: O19, only document's 2 rounds of 3; O20, a full grill with new questions.
- D13 (Q13): O21. One method for both modes. The new-look mode also makes its design file with the D12 grill, with hallmark's questions (audience, use, tone) added as first branches. Hallmark then builds from the finished design file. This replaces the "ask once" part of D7 for the new-look mode. Rejected: O22, hallmark's three questions only.
- D14 (Q12): O17. The new-look mode has two gates in all: the grill ends with the user confirming the design file (D12, D13), then one gate after the build, where the user sees the reference screen's screenshots and the Picks block (after the D6 checks and fixes) and says yes, gives changes, or asks for a different direction. Rejected: O18, a picks gate before the build (that would make three gates).
- D15 (Q14): O23. `puppeteer-core` is only a dependency of hallmark, for its render check. The lane checks its tools (node, `puppeteer-core`, Chrome or Chromium) at the start and, if one is missing, stops before any work and prints the exact install command. `st-init`'s tool check and `st-status` also check `puppeteer-core` and a browser. Which browser tools Stratum uses officially (Playwright, browser-skill, e2e tests) is a separate issue. Rejected: O24, continue with static checks only.
- D16 (Q15): O25. Done when (1) stub tests show the lane's skill files, the `/stratum:st` routing row, the `vendor.lock` entry and the new tool check are in place; (2) a new-look demo builds the same small brief the old way (`st-build` with `st-ui-ux`) and with the Design lane, and the user picks the lane's version from the screenshots; (3) an autonomous demo builds a new page in a project with a design file, it passes the D6 checks with no gate in the middle, and the user checks it after. Rejected: O26, stub tests and one demo with no comparison.
- D17 (Q16): O27. The lane never asks for `TOGETHER_API_KEY` and does not turn on image generation itself. It uses hallmark's real Wikimedia photos. Only if the user has set the key does hallmark use it, and the report says so. Rejected: O28, ask for a key and use generation when set.
- D18 (Q17, Q18): O29 with the O31 line. The Design lane works as a full frontend engineer for the screen: layout, components, styles, copy, pictures, motion, UI state, client-side form checks, loading, empty and error states, accessibility and keyboard use. Fast or Full owns what is behind the screen, test-first: API calls, data fetch and save, data model, sign-in, server code. Where real data is needed, the lane uses placeholder data of the same shape. `st-git` commits the lane's work after the user's gate (new look) or check (autonomous). Rejected: O30, the lane also builds the logic; O32, the lane owns only the look.
- D19 (Q19): O33. The lane writes component tests for the UI behavior it builds, with the project's own test runner, and runs them with the D6 checks before it hands over. The report lists them. If the project has no UI test runner, the report says the behavior is not tested, and the lane adds no new tool. Rejected: O34, no tests.
- D20 (Q20): O35. The new-look grill gets a "theme" branch: hallmark deals 3 themes with pictures, the user picks one, hallmark writes its tokens, and `st-impeccable document` scans them and writes `DESIGN.md` with real tokens and no new questions. FR-003's branch list gains "theme". Rejected: O36, document seed mode with its own interview.
- D21 (Q21): O39. Critique runs in full with its detector, split rule by rule: hallmark's sloplint owns every rule both check (measured 2026-10-24: 30 the same, 13 partly the same, of detect's 58), and the detector ignores those through `impeccable ignores`; the detector owns its 15 rules sloplint lacks (among them the 4 DESIGN.md drift rules, script errors, flat type hierarchy, clipped and overflowing layout). The rule map is built from the ids `impeccable detect --json` prints, and is checked again at each `st-sync`. Rejected: O37, critique without the detector (loses the 15 rules); O38, both in full (two owners).
