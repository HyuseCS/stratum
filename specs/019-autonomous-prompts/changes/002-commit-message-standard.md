# 002 commit-message-standard

What: One commit message standard (GitHub #97), written once in `agents/st-git.md` and pointed to by the worker brief and the session text. The git guard enforces the subject form and the no-attribution rule on every `git commit -m` command.
FRs: none in spec.md fit. #97 extends spec 019 decisions D4, D6, D8, D9 (`decisions.md`). Recorded as D21 in decisions.md ("one commit message standard").
Impact area: core runtime

## The standard (text to write in agents/st-git.md, step 6, replacing the current bullets)

1. Form: `git commit -m 'subject' -m 'body'`. Single quotes. No heredoc, no `-F`, no backticks, no `$(`, `${`, `<(`, `>(` anywhere in the message. Write an apostrophe as `'\''`.
2. Subject: `type(scope): what changed`, 72 characters or fewer, lower case type, no final period.
   - Types: feat, fix, refactor, docs, style, test, chore, spec, plan, sync.
   - Scope: the feature number (`019`), or an area word (`worker`, `ponytail`). Scope is optional.
   - `spec(NNN)` and `plan(NNN)`: spec and plan files of feature NNN. `sync(name)`: a synced upstream skill. `docs`: other text.
   - Version bump: exactly `Bump version to X.Y.Z`.
   - Merge and revert: git's own `Merge ...` and `Revert ...` subjects stay as they are.
3. Body: why, 1 to 3 lines, one `-m`. Name links by one form each: task `T012`, issue `#95`, PR `PR #92`, decision `D22`, review finding `F1`. No file lists, no diff retelling.
4. No AI attribution: no `Co-Authored-By:` trailer, no "Generated with" or "generated by" line.

## Risks
- R1: The guard now rejects any commit whose subject does not match, in every session including the user's own. Intended by #97, but a legit odd subject (`Initial commit`, `WIP`) is denied. The reason text says how to rewrite it.
- R2: Only `-m` commits are checked. An editor commit and `-F` with a file are not checked at all. Accepted: the form deny already blocks `-F` with a heredoc or `<(`.
- R3: The guard parses `-m` from shlex tokens. A `-m` value held in a shell variable (`-m "$MSG"`) is denied, since `$MSG` is not a valid subject.
- R6: On the guard's parse-error path (a line it cannot parse), a commit gets only `ask`, not deny, so a bad subject there is not denied.
- R4: Existing 48 guard fixtures change from `x` to `'fix: x'`. Mechanical, but check each still hits the branch it tests.
- R5: Another worker edits the lane briefs and `st-worker.sh` in parallel (#103). Touch only rule 5 in `st-worker.sh` and the commit sentence in `st-session-start.sh`.

## Open decisions
- Q1: Enforce body length in the guard? Default in this plan: no, advice only (1-3 lines) in the standard. Alternative: deny more than 5 body lines. I would keep it advice only.
- Q2: Subject scope required or optional? Default: optional, because `Bump version` and `Merge` are exempt and `docs: x` is common. Alternative: required for every type except `Bump`/`Merge`/`Revert`.
- Q3: Standard in `agents/st-git.md` only (this plan) or a new `docs/commit-standard.md`? I chose `st-git.md`: workers already must give rule 5 to the st-git agent, so it is the one place that is always loaded where commits happen.
