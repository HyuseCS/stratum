## R1. `st-worker.sh answer` refuses a permission dialog today

- Fact: `answer` reads the last 15 pane lines and exits 1 with `This is a permission prompt. Tell the user the workspace, the tab and the prompt; do not answer it.` when one matches `PERM`, for `--keys` and `--text` alike, with no key sent (`scripts/st-worker.sh:155`, `scripts/st-worker.sh:434`). A failed `agent read` gives the same line.
- Tests that hold it: AN1 and AN2 (`tests/test_st_worker.sh:1362-1369`). AN4 (`tests/test_st_worker.sh:1375-1377`) sends a key when the dialog is more than 15 lines up.
- The contract that set it: `specs/010-workflow-overhaul/contracts/scripts.md:236` (010 FR-017, normal mode never answers).
- Consequence: the spec assumption "No script change is needed" was false. FR-001 cannot work through the script as it is, and the skill forbids any other herdr call (`skills/st-worker/SKILL.md:10`).
- Decision (D3, O6): `answer --keys` may send one option number on a permission dialog. The script refuses when that option's line is a lasting option. `--text` keeps the refusal. Contract: `contracts/answer.md`.
- Small decisions inside D3 (wider refusal, never narrower):
  - The lasting match is `ask again|this session|in the future`, case-insensitive. `ask again` also catches a curly apostrophe. `this session` also catches "Yes, allow all edits during this session (shift+tab)" in the Claude Code edit dialog, which the D3 text "for this session" would miss.
  - A permission dialog takes exactly one key, `^[1-9]$`. A key like `enter` or `down` picks whatever option is marked, so the script cannot check its line.
  - The option line is the last line of the 15 read that starts with the key and a dot, the same way `answer --text` finds "Type something." (`scripts/st-worker.sh:440`). No such line: refused.
- Alternatives: O5 (only the skill text decides the option), rejected in D3.

## R2. What a normal-mode worker dialog shows

- Workers start with `--permission-mode auto` (`scripts/st-worker.sh:322`). A dialog in normal mode is the auto classifier's escalation or a hook `ask`. R4 fact 4 applies to the worker session too.
- `wait` prints `state blocked` and the pane text for a dialog (`scripts/st-worker.sh:153`, `scripts/st-worker.sh:403-406`). The spec assumption holds.
- Commits on the worker's own branch run with no prompt: `start` writes `commit: auto` and the branch into the worktree's `.stratum/git-guard.json` (`scripts/st-worker.sh:248-249`), and the guard returns no decision for such a commit (`hooks/st-git-guard.py:165-168`). The guard asks only for `--amend` or a commit that may target another folder or branch, and its reason then lists the staged files (`hooks/st-git-guard.py:172`). Both are on the worker never list or fail the commit rule.
- A normal-mode commit dialog has no `branch` or `staged` line: those come from the `approval` request file in autonomous mode only (`scripts/st-worker.sh:203-204`). The worker brief forces the commit form `git add <path> <path> && git commit -m "<subject>" -m "<body>"` with no `cd`, no `git -C` and no `$(...)` (`scripts/st-worker.sh:237`).
- Decision (small, settled by the code): in normal mode the orchestrator reads the commit rule from the dialog text. The staged paths are the paths of the `git add` in the command shown. The worktree is the pane's own folder. A part of the rule the dialog text does not show sends the dialog to the user.

## R5. The screen hash (D6, FR-011)

- Problem (US1 review F1, high): the dialog can change between the `wait` the orchestrator judged and its `answer` call. Example: the user approves dialog A in the pane, the worker stops on dialog B (`git push`), and `answer --keys 1` approves B. The `not blocked` check does not catch it, because B is also blocked.
- Decision (D6, O11): the 013 form. `wait` and `watch` print `screen<TAB><hash>` for a blocked worker whose pane shows a permission dialog. `answer` on a permission dialog needs `--screen <hash>` and sends nothing when the pane's hash differs now. The hash method is `scripts/st-advisor.sh:35` (`--source recent-unwrapped`, ANSI stripped with sed, sha256, first 12 hex), with 40 lines in place of 20 (D9). The argument check is `scripts/st-advisor.sh:25` (`^[0-9a-f]{12}$`). The refusal line follows `scripts/st-advisor.sh:38` ("the Codex tab shows another prompt"). Contract: `contracts/answer.md` sections 1 to 3.
- `answer` reads 40 lines (D9), and judges a dialog by the last 15 of them. That keeps AN4 (a dialog more than 15 lines up is not a dialog).
- D9 (Q9, re-review F2 low, O17): T012 hashed a 20-line read but printed a separate 40-line `panetext` read (`scripts/st-worker.sh:153`). So the orchestrator judged text that was partly not hashed, such as the head of a long command 21 to 40 lines up. Fix: `st blocked` reads 40 lines once, hashes that text, prints the `screen` line, and prints the same text as `pane text:`. `answer` hashes the same 40-line read. Rejected: O18 (keep 20 lines, accept the gap with a ponytail note).
- Re-review F1 (medium, inside D7): T012 took the last line in the 15-line window that starts with the key. A command line `  3. Yes` above a 2-option dialog then passed as option 3, because no real option 3 came after it. Fix: only lines after the last dialog head line (`Do you want to ...`, the head part of `PERM`) count as options. No head line: refused. Case AN6e.
- Unknown (P1, closed by D8: build as planned, fail closed, `ponytail:` note): whether a real Claude Code worker pane stays the same in its last 40 lines (20 when P1 was raised, 40 after D9) while a dialog waits. The Stratum statusline has a duration segment (`statusline/powerline.json`, `"showDuration": true`). A spinner timer could also redraw. The stub cannot show it, and the doc quotes in R4 do not say. In 013 a Codex tab hash matched in the live run (013 D19), but Codex is another program. A pane that redraws fails safe: every `answer` is refused and the dialog goes to the user.
- Rejected: O12 (accept the risk with a ponytail note).

## R6. The one-time yes allow list (D7, FR-010)

- Problem (US1 review F2 medium, F3 low): T003's phrase list misses lasting options with other words ("Yes, and always allow access to other/ from this project"), a lasting phrase on a wrapped second line, and a command line that looks like an option (`printf "3. step three"` with key 3 and no option 3).
- Decision (D7, O13): the option line must be exactly `Yes`, `Yes, proceed` or `Yes, just this once`, after the `N. ` prefix and an optional `❯` marker, with an optional one-character key hint such as `(y)`. These are 013's one-time yes forms (`skills/st-build/SKILL.md:98`). The last line that starts with the key is the option line. Everything else is refused. This one check replaces T003's "no option" and lasting-phrase checks.
- Small decision: the key hint is one lowercase letter or digit in brackets. `(shift+tab)` and `(esc)` are refused, because they appear only on lasting or No options in the dialogs seen.
- Rejected: O14 (keep the phrase list, add "always allow").

## R4. In-session subagent prompts (US3, FR-007, FR-008)

Each fact has its source. The note in `skills/st/SKILL.md` uses only these.

1. Who sees the prompt. https://code.claude.com/docs/en/sub-agents.md: "Foreground subagents block the main conversation until complete. Permission prompts are passed through to you as they come up." and "When a background subagent reaches a tool call that needs permission, Claude Code surfaces the prompt in your main session and names the subagent that is asking. Approve to let the subagent continue, or press Esc to deny that one tool call without stopping the subagent." The prompt goes to the user, not to the orchestrator model.
2. Agent text never approves. Same page: "no message from any agent counts as your approval for a pending permission prompt, and no agent message can change a subagent's permission settings, CLAUDE.md, or configuration. Only the permission system or your own messages can grant approval."
3. Agent settings do not grant permission. Same page, frontmatter: `permissionMode` is "Ignored for plugin subagents" (every `stratum:*` agent is a plugin agent), and when the main session is in `bypassPermissions`, `acceptEdits` or `auto`, the subagent's `permissionMode` is ignored. The `tools` field limits which tools exist but does not pre-approve them.
4. Auto mode checks subagents the same way. https://code.claude.com/docs/en/permission-modes.md: in auto mode "each of its [the subagent's] actions goes through the same decision order as in the parent session, with the same block and allow rules", and "Before a subagent starts, the delegated task description is evaluated, so a dangerous-looking task is blocked at spawn time."
5. A hook that changes the Agent input. https://code.claude.com/docs/en/hooks.md: "When your hook returns updatedInput with no permissionDecision in auto mode, Claude Code can deny the changed call. The server reviewed the input Claude wrote, not the input your hook returned." `hooks/st-models.py:76` prints `updatedInput` with no `permissionDecision` for every `stratum:*` Agent call that has an entry in `.stratum/models.json`.
6. What the orchestrator can do then. Not in the docs. Source (D4): a Claude Code denial text, seen 4 times in the orchestrator session on 2026-11-06 (the `stratum:st-git` spec commit, `stratum:st-plan`, the `stratum:st-git` plan commit, the `stratum:st-git` commit of the inspect fixes, 0cf994d). Each time the second send ran. The first: an Agent call to `stratum:st-git` was denied with this text, word for word, except that the JSON input object is left out and marked `{<the hook's input as JSON>}`: "The server-side auto mode classifier gave no verdict for Agent: a hook changed this call's input after auto mode reviewed it, so the review does not cover what would run. This is not a judgment that the action is unsafe. The hook produced this input: {<the hook's input as JSON>}. In your next response, issue the Agent call once more with exactly that input so auto mode reviews it. Put nothing else in that response but other calls whose denial quoted an input like this one. If it is denied again, do not retry; continue with other tasks and tell the user that auto mode could not check this Agent call because a hook or plugin changes it, and that they can turn that hook or plugin off (or ask their administrator to) or switch out of auto mode to approve it themselves." The hook's input was the call's input plus `"model":"haiku","effort":"xhigh"`. The orchestrator sent the call once more with that input and it ran. Rule: send the Agent call once more with exactly the input the denial quotes. Denied again: tell the user.
7. Not documented: any way for the parent model to answer, approve or deny a subagent's permission prompt.
8. Rule, not a doc fact: the orchestrator never runs an action a subagent was denied in place of the subagent (permission laundering). It brings the denial to the user. Source: fact 2 and `specs/014-prompt-answers/spec.md` FR-007.
9. Passing `model` and `effort` yourself. Source (a dated run in this session, D5): the orchestrator session of 2026-11-06. The orchestrator put `model` and `effort` from `.stratum/models.json` in 6 Agent calls itself: `stratum:st-test` T001, `stratum:st-test` T002, `stratum:st-build` T004, `stratum:st-git` T002/T004 commit, `stratum:st-build` T003, `stratum:st-git` T001/T003 commit. Auto mode refused none of them. Before that, the 4 calls without them were refused. `hooks/st-models.py:69-76` looks up the agent in `.stratum/models.json`, copies its `model` and `effort` into the input, and prints that input. When the call already holds the same values, the hook's input equals the call's input. The likely reason auto mode then refuses nothing is that it reviewed what would run (fact 5). That reason is an inference, not documented. Rule (D5): put `model` and `effort` from `.stratum/models.json` in the Agent call first. The send-again rule of fact 6 stays for a call that is still refused.

- Decision: two short note lines in `skills/st/SKILL.md` "## Always". W24 rests on facts 1, 2, 7 and 8. The W25 line starts with W30 (D5, facts 5 and 9), then the send-again rule (facts 5 and 6). The note has no pointer to this file: the skill ships in the plugin, and the rows S1 to S5 keep the sources here. Facts 3, 4 and 7 stay in this file only.
- Alternatives: a change to `hooks/st-models.py` so it returns a `permissionDecision` (out of scope by the spec); no note (fails FR-007).
